## Per-defect fix spec

### D-1 — Subscription Key custom row in Settings UI

**Where:** `package.json#contributes.configuration`, `src/strings.ts`,
`src/settings/schema.ts`.

**Change:** add a fake property `minimaxUsage.subscriptionKey`
with `type: null` and a `markdownDescription` containing a clickable
command link. The link target is `command:minimaxUsage.setApiKey`.
The text uses a new `STR_SETTINGS_APIKEY_LINK` string in
`src/strings.ts`:
- "Click [Set your API key](command:minimaxUsage.setApiKey) to set or update your Subscription Key."

The architecture document (`.kitchen/architecture/extension-architecture.md` § 5.1) and the UI spec (`.kitchen/design/ui-spec-v0.1.0.md` § 10.1) both commit to this row. The architecture gets a follow-up note that the build's row uses the `markdownDescription` + command-URI pattern; this is the standard VSCode mechanism for custom settings rows.

**Phase 04 review nit (related):** the trailing period on
`STR_SETTINGS_REGION_ENUM_0` and `STR_SETTINGS_REGION_ENUM_1`
(from the re-review report) is also fixed here for consistency.
The strings doc is updated to match the build's exact text.

### D-2 — Post-key-save refresh

**Where:** `src/extension.ts:113-145` (the `setApiKey` command).

**Change:** after `await secretStorage.setApiKey(value)`, the
command explicitly does:
1. `await cache.invalidateAll()`
2. `void controller.refreshNow("api-key-change", { forceRefresh: true })`
3. `void statusBar.render()`

The existing `onDidChangeApiKey` listener at `src/extension.ts:105-110`
stays — it's correct for cross-extension changes (a future
extension rotating the key would fire it). The same-extension path
is now explicit.

**Side effect:** the secondary `src/secrets/secretStorage.ts:30` bug
(`h(undefined)` — handlers are called with `undefined` instead of
the new key) is also fixed: change to `h(SECRET_API_KEY)` so future
handlers that need the value can read it. The current handlers
don't depend on the value, but the contract is cleaner with the
right value.

### D-3 + D-4 — Status bar click + modal template

**Where:** `src/ui/webview/usageModal.ts:11-24` and `:54-55`.

**Change:**
1. `readBundledHtml` becomes a method on the class (or takes the
   `context` as a parameter). It reads from
   `context.extensionPath/dist/webview/modal.html` only — the
   fallback to the source-tree path is removed (the source path
   is irrelevant at runtime; only the bundled path matters).
2. The `WebviewPanel`'s `ViewColumn` changes from `Beside` to
   `Active`. The modal is a usage display, not a side-by-side
   editor; `Active` opens it in the user's current column.
3. Add a build-time check: in `esbuild.config.mjs`, after
   `copyStaticAssets()`, verify that `dist/webview/modal.html`
   exists. If not, the build fails with a clear error.
4. Add a unit test in `test/api/usageModal.test.ts` (or a new
   `test/ui/usageModal.test.ts`) that exercises the readHtml path
   with a stub `context.extensionPath`. The test asserts the
   correct file is read and the fallback is not used.

### D-5 — `*` activation event

**Where:** `package.json#activationEvents`.

**Change:** from `["*"]` to:
```json
["onStartupFinished", "onCommand:minimaxUsage.setApiKey", "onCommand:minimaxUsage.showUsage", "onCommand:minimaxUsage.openSettings"]
```

The status bar appears on `onStartupFinished` (a few seconds after
VSCode opens, not before). The commands work via `onCommand:*`
even if invoked before startup finishes. The `vsce` warning goes
away. The `extension.ts` activation flow is unchanged — it still
runs once on any of these events.

**Architecture follow-up:** `.kitchen/architecture/extension-architecture.md` § 3 needs a one-line update: replace the
commitment to `*` with the rationale for the split. The orchestrator
updates the architecture doc in the same commit as the
`package.json` change, with a clear ADR-style note.
