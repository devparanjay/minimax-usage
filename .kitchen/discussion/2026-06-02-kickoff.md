# Kickoff Discussion — 2026-06-02

**Participants:** project owner, FooFoo (orchestrator, Dreamy Devs)
**Scope:** project kickoff — what we are building, how we will work, and
the governance rules we will follow.

## Context

The project owner wants a VSCode extension that shows near-realtime usage
of their MiniMax plan inside VSCode — usage they would otherwise have to
check on the MiniMax platform's account page. The extension is for
personal use by the project owner and will be distributed only through the
VSCode Marketplace.

The project is at `main` with a single initial commit (LICENSE — AGPL v3)
and an empty `images/icons/` directory. The starting state is a clean slate.

## Decisions Made

### Project identity

- **Project / repo name:** `minimax-usage`
- **Extension display name:** `MiniMax Usage`
- **Distribution channel:** VSCode Marketplace only. No release, no
  publication, no distribution through any other public or private
  channel on any other platform. → See ADR `0001`.

### Governance rules (project-wide)

These rules apply to every version and every phase of the project.

- **Branching:** No direct work on `main`. For every major version, cut a
  new branch (e.g. `v0.1.0`). Minor versions get their own branch off the
  major version branch (e.g. `v0.1.1` off `v0.1.0`). → See ADR `0002`.
- **Merging:** All branches — including version branches — merge through
  a pull request with a review. No direct merges.
- **Commits:** Atomic commits following the Conventional Commits
  convention.
- **Documentation layers:**
  - User-facing docs in `/docs/`.
  - Internal docs in `.kitchen/`.
- **Project-root-relative paths only.** No local machine paths, no local
  data, no environment-specific references in code, comments, or docs.
- **Sensitive data is gitignored** throughout the project.
- **Roadmaps in increasing granularity:**
  - Project-wide roadmap
  - Per-version roadmap + timeline
  - Per-phase plan
  - Per-phase task list
  - Roadmaps are kept current as work progresses.
- **Major decisions and security/device/OS risk decisions** are escalated
  to the project owner. The team does not act unilaterally on these.

### Version strategy

- Each version branch gets a release when it is ready.
- The release on `main` is the one published to the VSCode Marketplace.
- See ADR `0002`.

### API discovery approach

- The project owner does not have the exact API spec to hand.
- The team will:
  1. Check the MiniMax official docs at
     `https://platform.minimax.io/docs/` and
     `https://platform.minimax.io/docs/api-reference/api-overview`.
  2. Take **reference only** (no code copying) from the open-source repo
     `https://github.com/JochenYang/minimax-status` to understand how
     usage data is fetched from the MiniMax API.
- See ADR `0003`.

### Publishing

- The publish pipeline is wired as a GitHub Actions workflow.
- The workflow references a `VSCE_PAT` repository secret for the
  Marketplace Personal Access Token.
- The project owner will add the actual `VSCE_PAT` value to GitHub
  Secrets themselves. The team does not handle the token value at any
  point.
- See ADR `0004`.

### Credentials & secrets

- The project owner will provide any credentials (API key for testing,
  `VSCE_PAT` for publishing) directly when needed.
- The team uses placeholders in code and CI configuration; the project
  owner substitutes real values locally or via Secrets.

## Open Items

- **API contract** — once `solution-architect` finishes discovery
  (MiniMax official docs + reference repo), the exact endpoint paths,
  response shapes, and auth header are captured in
  `.kitchen/architecture/api-contract.md` and reviewed.
- **API key for testing** — the project owner will provide a real API
  key when the extension is ready for end-to-end testing. The team will
  have placeholder-based testing in the meantime.
- **`VSCE_PAT`** — the project owner adds the secret before the first
  Marketplace publish.
- **Publisher identity** — VSCode Marketplace requires a publisher
  namespace. The project owner will confirm or create the publisher
  account; the team will configure the extension manifest accordingly.
